# user_mgmt_gitops

Ops repository for the **User Management Service**. It contains everything needed to run the
app on Kubernetes — nothing else. The application source code lives in
[`user_mgmt_service`](https://github.com/Luca-Guettinger/user_mgmt_service).

```
charts/user-mgmt/         Helm chart (the whole app, templated)
  Chart.yaml              chart metadata
  values.yaml             all default configuration values
  values-staging.yaml     overrides for the staging namespace
  values-dev.yaml         overrides for the local kind cluster (not managed by ArgoCD)
  values-prod.yaml        overrides for the DigitalOcean cluster
  templates/              the Kubernetes manifests as Go templates
    _helpers.tpl          reusable template functions
argocd/                   ArgoCD Application + Project manifests
local/kind-cluster.yaml   local kind cluster definition
docs/tls-setup.md         how the HTTPS certificate is obtained
```

---

## 1. What each Kubernetes piece does

The app has three components. Each one gets a **Deployment** (runs the container) and a
**Service** (a stable in-cluster DNS name for it).

| Piece | What it does |
|---|---|
| **Deployment** `frontend` | Runs the Next.js portal container (port 3000). |
| **Deployment** `backend` | Runs the Spring Boot API container (port 8080). |
| **Deployment** `postgres` | Runs the PostgreSQL container (port 5432). |
| **Service** (one per component) | Gives the pod a fixed name like `user-mgmt-postgres`. Pods get new IPs whenever they restart; the Service name never changes. The backend reaches the DB *only* through this name, never through a pod IP. |
| **ConfigMap** | Non-secret settings as key/value pairs, injected into the container as environment variables — `SPRING_DATASOURCE_URL`, `JWT_ISSUER`, `NEXT_PUBLIC_API_URL`, … |
| **Secret** | Same idea, but for sensitive values: DB username/password and `JWT_SECRET`. |
| **PersistentVolumeClaim** (`user-mgmt-postgres-data`) | Asks the cluster for a disk. Without it Postgres writes into the container's own filesystem and **all data is lost every time the pod restarts**. The claim is bound to a real DigitalOcean block-storage volume and mounted at `/var/lib/postgresql/data`. |
| **Ingress** | The single HTTP(S) entrypoint from the internet. Routes `/backend/*` to the backend Service (stripping the `/backend` prefix) and everything else to the frontend Service. Also holds the TLS certificate. |
| **ClusterIssuer** | Tells cert-manager how to fetch a free Let's Encrypt certificate for the ingress host. |

Two details worth remembering:

- The Postgres volume is `ReadWriteOnce` — only one node may mount it at a time — so the
  Postgres Deployment uses `strategy: Recreate` (kill the old pod, *then* start the new one).
  A normal rolling update would deadlock waiting for the volume.
- Postgres refuses to initialise on a volume whose root contains `lost+found`, which block
  storage always has. So the data directory is a subdirectory of the volume: `subPath: pgdata`.

## 2. What Helm charts do

Plain manifests are static files. To run the same app in dev and prod you copy the folder and
hand-edit image tags, hostnames, replica counts and passwords in a dozen places.

A **Helm chart** is a package of manifest *templates* plus one file of values. Helm renders the
templates with the values and applies the result. Same chart, different values file →
different environment, nothing duplicated.

### What changed to move from manifests to a chart

| Before (`kubernetes/*.yaml`) | After (`charts/user-mgmt/`) |
|---|---|
| 8 static files with the values written into them | The same objects as templates; every value comes from `values.yaml` |
| Image tags, hostnames, ports, passwords hardcoded in each file | All in `values.yaml`; staging/prod list only the differences in `values-staging.yaml` / `values-prod.yaml` |
| Names like `backend`, `postgres` typed into every file and every cross-reference | Generated by `_helpers.tpl` (`user-mgmt.componentName`), so a rename happens in one place |
| Labels copy-pasted onto every object | The `user-mgmt.labels` / `user-mgmt.selectorLabels` helpers |
| `jdbc:postgresql://postgres:5432/userdb` written by hand — silently breaks if the Service is renamed | Built by the `user-mgmt.datasourceUrl` helper from the Postgres values, as a fully-qualified name |
| DB credentials duplicated as two differently-named env vars in two files | One `user-mgmt.dbCredentialEnv` helper, called with the variable names each component wants |
| **No PersistentVolumeClaim at all** — DB data was ephemeral | `templates/postgres/pvc.yaml`, switchable and sizeable via `postgres.persistence.*` |
| Namespace never mentioned; everything landed in `default` | Every object carries `namespace: {{ include "user-mgmt.namespace" . }}`, which follows the release / ArgoCD target namespace |
| `NodePort` Services for outside access | `ClusterIP` + Ingress in prod; NodePort stays available via `values-dev.yaml` |
| `traefik/dynamic.yml` did the routing | `templates/ingress/ingress.yaml` (nginx ingress) |

`_helpers.tpl` holds the reusable functions: `user-mgmt.name`, `user-mgmt.fullname`,
`user-mgmt.componentName`, `user-mgmt.componentFqdn`, `user-mgmt.namespace`,
`user-mgmt.chart`, `user-mgmt.labels`, `user-mgmt.selectorLabels`, `user-mgmt.image`,
`user-mgmt.imagePullPolicy`, `user-mgmt.datasourceUrl`, `user-mgmt.postgresSecretName`,
`user-mgmt.dbCredentialEnv`.

Validate and preview the chart at any time:

```bash
helm lint charts/user-mgmt
helm lint charts/user-mgmt -f charts/user-mgmt/values-prod.yaml

helm template user-mgmt charts/user-mgmt \
  -f charts/user-mgmt/values.yaml -f charts/user-mgmt/values-prod.yaml -n user-mgmt
```

## 3. What ArgoCD does

Without ArgoCD you deploy by running `helm upgrade` from your laptop, and whatever is in the
cluster is whatever the last person happened to run.

**ArgoCD inverts that.** It runs *inside* the cluster, watches this Git repository, and
continuously compares the rendered chart against the live cluster. Git becomes the single
source of truth:

- Push a change to `values-prod.yaml` → ArgoCD notices and applies it. No `kubectl` needed.
- Someone edits a Deployment by hand in the cluster → `selfHeal: true` reverts it.
- Delete a template from Git → `prune: true` deletes the object from the cluster.

### What was added for ArgoCD

| File | Purpose |
|---|---|
| `argocd/application-prod.yaml` | The `Application` object: *render `charts/user-mgmt` from this repo with `values.yaml` + `values-prod.yaml`, and keep namespace `user-mgmt` in sync with it*. Sync is `automated` with `prune` + `selfHeal`. |
| `argocd/application-staging.yaml` | The same chart with staging values, into namespace `user-mgmt-staging`. Smaller resource envelope, no ingress. |
| `argocd/project.yaml` | An `AppProject` restricting what this app may touch: only this Git repo, only the `user-mgmt*` namespaces, and the one cluster-scoped resource it needs (the cert-manager `ClusterIssuer`). |

Namespace layout — the app is deliberately **not** in ArgoCD's namespace:

```
namespace argocd          ArgoCD itself + the Application / AppProject objects
namespace user-mgmt       the actual app (frontend, backend, postgres, PVC, ingress)
namespace user-mgmt-staging  second environment, same chart, own ResourceQuota
```

`CreateNamespace=true` in the Application means ArgoCD creates the target namespace itself.

## 4. Deploying to the DigitalOcean cluster

Prerequisites: `kubectl` pointed at the cluster (`kubectl config current-context` →
`do-fra1-kube`) and `helm` installed. ArgoCD already runs in the `argocd` namespace.

### Step 0 — create the cluster

The cheapest node size DOKS offers is `s-1vcpu-2gb` (12 USD/month). `values-prod.yaml` sets
resource limits and caps the JVM heap so the whole app plus ArgoCD fits on one such node.
**Do not enable the HA control plane** — the standard control plane is free, HA costs 40
USD/month.

```bash
doctl kubernetes cluster create teko-kube   --region fra1 --version latest   --node-pool "name=pool;size=s-1vcpu-2gb;count=1" --wait
```

RAM is tight on 2 GB. ArgoCD ships three components this setup does not use — scale them to
zero right after installing it:

```bash
kubectl -n argocd scale deploy/argocd-dex-server   deploy/argocd-applicationset-controller   deploy/argocd-notifications-controller --replicas=0
```

### Step 1 — push this repo to GitHub

ArgoCD can only read the chart from a Git URL, so this has to exist first.

```bash
cd user_mgmt_gitops
gh repo create Luca-Guettinger/user_mgmt_gitops --public --source=. --remote=origin --push
```

If you make it private instead, register credentials in ArgoCD once:

```bash
argocd repo add https://github.com/Luca-Guettinger/user_mgmt_gitops.git \
  --username <user> --password <token>
```

### Step 2 — install the nginx ingress controller

This makes DigitalOcean provision a Load Balancer with a public IP (~12 USD/month, covered by
the 200 USD / 60-day trial credit).

> **Don't try to skip the Load Balancer with `hostPort`.** DOKS worker nodes sit behind a
> DigitalOcean-managed firewall that only opens the NodePort range 30000-32767. Ports 80 and
> 443 are silently dropped (connection *times out*, it is not refused), so an ingress
> controller on `hostPort: 80` is unreachable from the internet — and without port 80 the
> Let's Encrypt HTTP-01 challenge cannot complete either. Verified by probing a node directly:
> port 30300 answered, ports 80/443 timed out. The only free workaround is adding an inbound
> rule for 80/443 to the auto-created `k8s-<cluster-id>` firewall, which DigitalOcean may
> reconcile away again.

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.3/deploy/static/provider/cloud/deploy.yaml
kubectl -n ingress-nginx get svc ingress-nginx-controller -w    # wait for EXTERNAL-IP
```

### Step 3 — point DNS at that IP

The domain is on Cloudflare. **DNS → Records → Add record:**

| Field | Value |
|---|---|
| Type | `A` |
| Name | `vsc` |
| IPv4 address | the Load Balancer `EXTERNAL-IP` from step 2 |
| Proxy status | **DNS only** (grey cloud) |
| TTL | Auto |

The grey cloud matters. With the proxy enabled, Cloudflare's *Always Use HTTPS* redirects the
ACME HTTP-01 challenge to https before a certificate exists, so cert-manager never gets one;
and SSL mode *Flexible* plus the ingress controller's own HTTPS redirect produces a redirect
loop. Turn the proxy on only after the certificate has been issued, and then set the SSL/TLS
mode to *Full (strict)*, never *Flexible*.

### Step 4 — install cert-manager

Required because `values-prod.yaml` enables TLS and creates a `ClusterIssuer`. Install it
*before* ArgoCD syncs, otherwise the sync fails on the missing CRD.

```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.16.2/cert-manager.yaml
kubectl -n cert-manager rollout status deploy/cert-manager-webhook
```

To skip TLS for now instead, set `ingress.tls.enabled: false` and
`certManager.clusterIssuer.create: false` in `values-prod.yaml`.

### Step 5 — set the real database password

`values-prod.yaml` ships `postgres.auth.password: change-me`. Change it before the first
deploy — that value is what initialises the database.

### Step 6 — rebuild the frontend image

`NEXT_PUBLIC_API_URL` is compiled into the Next.js bundle at **build** time, so setting it in
the ConfigMap alone does nothing. In the `user_mgmt_service` repo:

```bash
docker build --build-arg NEXT_PUBLIC_API_URL=https://vsc.notenverwaltung.ch/backend \
  -t ghcr.io/luca-guettinger/auth-portal:latest ./auth_portal-main
docker push ghcr.io/luca-guettinger/auth-portal:latest
```

### Step 7 — hand it over to ArgoCD

```bash
kubectl apply -f argocd/project.yaml
kubectl apply -f argocd/application-prod.yaml
kubectl apply -f argocd/application-staging.yaml
```

ArgoCD creates the `user-mgmt` namespace and deploys everything. Watch it:

```bash
kubectl -n argocd get application user-mgmt-prod -w
kubectl -n user-mgmt get pods,pvc,ingress
kubectl -n user-mgmt get certificate         # READY=True once the cert is issued
```

### Step 8 — clean up the old release

The old static manifests were applied into the `default` namespace. Remove them so they don't
sit around next to the new deployment:

```bash
kubectl -n default delete deploy backend frontend postgres
kubectl -n default delete svc backend frontend postgres
kubectl -n default delete cm backend-config frontend-config postgres-config
kubectl -n default delete secret backend-secret postgres-secret
```

The old Postgres had no volume, so there is no data to migrate.

### Step 9 — open the app

<https://vsc.notenverwaltung.ch>

```bash
# initial admin password

kubectl -n argocd port-forward svc/argocd-server 8080:443
```

## 6. Everyday workflow

Change a value, commit, push. That is the whole deploy.

```bash
vim charts/user-mgmt/values-prod.yaml
git commit -am "bump backend replicas"
git push
```

ArgoCD picks it up within ~3 minutes, or force it immediately with
`argocd app sync user-mgmt-prod`.

### Running the chart without ArgoCD

Useful for testing before pushing:

```bash
helm upgrade --install user-mgmt charts/user-mgmt \
  -f charts/user-mgmt/values.yaml -f charts/user-mgmt/values-prod.yaml \
  -n user-mgmt --create-namespace
```

Locally on kind: `kind create cluster --config local/kind-cluster.yaml`, then the same command
with `values-dev.yaml` and `-n user-mgmt-dev`. That path is for kind only; the
staging environment in the shared cluster is driven by ArgoCD from
`values-staging.yaml`.

## 7. What this costs

The control plane is free; you pay for the worker node, the Load Balancer and the volume.

| Item | Price | Note |
|---|---|---|
| Worker node `s-1vcpu-2gb` | 12 USD/month | cheapest size DOKS offers |
| Load Balancer | 12 USD/month | created by the ingress-nginx install |
| Block storage (PVC) | 0.10 USD/GiB/month | `values-prod.yaml` asks for 1 GiB |
| Bandwidth | 0 USD | 2000 GiB per node included |
| Container registry | 0 USD | images live on GHCR, not DOCR |

**Total: about 24 USD/month.** Avoid the two expensive extras: the HA control plane
(+40 USD/month) and a DigitalOcean Container Registry (not needed).

Everything is billed **hourly and prorated**, so a cluster that only runs while you work on it
costs very little — roughly 0.80 USD per day, 5.60 USD per week. Tear it down when you are done:

```bash
doctl kubernetes cluster delete teko-kube
# The Load Balancer is not always removed with the cluster - check and delete it,
# otherwise it keeps billing 12 USD/month:
doctl compute load-balancer list
```

`values-prod.yaml` deliberately uses `storageClass: do-block-storage` (reclaim policy
*Delete*) and `keepOnDelete: false`, so the volume disappears with the PVC instead of becoming
an orphan that keeps costing money. For data you actually want to survive, switch to
`do-block-storage-retain` and `keepOnDelete: true` — and then remember to delete the volume
by hand.

### Running without the Load Balancer (about 12 USD/month)

Add an inbound rule for TCP 80 and 443 to the auto-created `k8s-<cluster-id>` firewall in the
DigitalOcean control panel, then install ingress-nginx with `hostPort` instead of a
LoadBalancer Service:

```bash
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install ingress-nginx ingress-nginx/ingress-nginx   -n ingress-nginx --create-namespace   --set controller.kind=DaemonSet   --set controller.service.type=ClusterIP   --set controller.hostPort.enabled=true
```

Point DNS at the node's public IP instead of the Load Balancer IP. Nothing in the chart
changes. The catch: that firewall is managed by DigitalOcean and the rule can be reconciled
away (for example on a node-pool upgrade), which takes the app offline until you re-add it.
